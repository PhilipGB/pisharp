# PiSharp parity matrix

This matrix tracks observable compatibility with Pi `main` at revision
`d7296c063b7971a7298769cfff1a167a9a16f8ed`. It is deliberately separate from
feature marketing in `README.md`: a capability is not considered complete until
its behaviour has a conformance test or an explicit intentional-difference note.

Status values:

- **Exact** — the public shape and observable behaviour are intended to match.
- **Equivalent** — the implementation differs internally but has the same user-facing contract.
- **Partial** — the main path exists, but important behaviour or protocol details are missing.
- **Missing** — not implemented.
- **Intentional difference** — deliberately outside the current .NET product boundary.

Pi paths below are relative to `/tmp/pi-reference` in the development
checkout. The reference fixture inputs in `tests/PiSharp.Core.Tests/Fixtures/pi-v3`
are copied/reduced from the pinned source contracts and are not generated by
PiSharp.

Intentional differences in this area:

- **Agent directory**: the model/auth subsystem (auth.json, models.json) uses `PISHARP_AGENT_DIR`, falling back to `~/.pisharp`, per the port contract; the Phase 1 settings subsystem keeps the pinned `PI_CODING_AGENT_DIR`/`~/.pi/agent` paths. With neither variable set the two subsystems live in different trees.
- **Login surface**: `/login` runs the pinned provider/method selection and credential flows in a plain text console (`ConsoleAuthInteraction`) over the `IConsoleIO` seam; secrets are masked per key (echoed as `*`, never the secret), Esc cancels a prompt, and the cancellation token is observed between keys (a blocked `Console.ReadLine` cannot be interrupted on Unix, so interactive prompts are key-driven — redirected stdin falls back to a plain line read where masking is impossible). Multi-match selection is a numbered list instead of the TUI dialog.
- **`/llama` surface and progress**: the pinned TUI model picker (SelectList) and live SSE download/load progress bars are ported as a text menu (numbered list + `d` for download); load/unload/download progress is polled from the router status (`LoadAndWaitAsync`/`DownloadAndWaitAsync` re-query `/models` and report the same `done/total` progress the SSE stream would) instead of subscribing to the router's event stream — same states and terminal conditions, coarser progress updates.
- **llama.cpp built-in registration**: pinned ships llama.cpp as the bundled `/llama` extension (registered when the extension loads); PiSharp registers it as a built-in provider in the default runtime, so it appears in `/login` and `--list-models` without an extension step. The pi.dev remote-catalog overlay is skipped for `llama.cpp` (its catalog is the local router, not pi.dev).
- **Serialized runtime refreshes**: pinned's `registerProvider`/`unregisterProvider` fire `void this.refresh({ allowNetwork: false })` (a full rebuild + refresh) without awaiting, and `ModelRuntime.refresh` itself can be called concurrently. A concurrent rebuild supersedes the in-flight refresh's controller, cancelling it; the provider phase then aborts mid-flight and the cancellation filter (`if (!signal.aborted)`) swallows it — the caller's refresh returns "success" with its live phase silently discarded. The pinned code shares this latent race; PiSharp serializes runtime `RefreshAsync` calls (a per-runtime gate) so the background rebuild from registration completes before the next refresh rebuilds, removing the cancellation-of-in-flight-refresh path. The background refresh is also tracked (`PendingRefresh` / `LastRefreshError`) so a caller can await the catalog settling after a registration change and query a failed refresh — the pinned `void` fire-and-forget gives no signal at all.
- **Interactive commands are between-turns only**: `/model`, `/thinking`, `/login`, and `/logout` execute between turns; typed during a streaming turn they queue as steering input, matching the PiSharp turn model rather than the pinned live-in-turn command handling.
- **Model banner**: the one-line startup banner shows the resolved model at launch; `/model`/`/thinking` report the new state inline rather than re-rendering a pinned-style live TUI footer.

## Conformance fixtures

Fixtures are intentionally small, deterministic contract samples:

- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/pi-session.jsonl` — Pi v3 header and typed message entries.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/settings/global-settings.json`, `project-settings.json` — two-scope settings merge with per-model compaction overrides and package sources.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/settings/settings-legacy.json` — legacy settings shapes that must migrate to the current format.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/json-events.jsonl` — lifecycle, message delta, tool, retry, and compaction event shapes.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/rpc-requests.jsonl` — representative current RPC commands.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/tool-schemas.json` — Pi's normal coding-tool names and schema anchors.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/prompt-template.md` — placeholder expansion contract.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/skill/SKILL.md` — skill frontmatter contract.
- `tests/PiSharp.Core.Tests/Fixtures/pi-v3/package.json` — `pi` package manifest contract.

The fixtures are compatibility inputs, not claims that the current implementation
already consumes every shape. Phase 10 and later will turn the remaining protocol
fixtures into executable golden comparisons as the corresponding application-owned
models are introduced; the settings fixtures are already exercised by
`SettingsManagerTests`.

## Update rule

When upstream Pi changes, update the pinned revision, add or revise the relevant
fixture, change the matrix status, and add a conformance test before changing
runtime behaviour. Intentional .NET differences must name the affected capability
and remain explicit here.
