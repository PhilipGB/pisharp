## PiSharp gap and implementation order

PiSharp now has a general `PiSharpToolRegistry` with immutable registered/callable/declared projections; all five exposure states; prepare-loadout description and declaration filtering; extension registration metadata; per-`AgentSession` loadouts; request-time MAF tool declaration projection; an extension execution context for changing active tools; and a fail-closed invocation guard. Loadout events persist the active names on session branches and round-trip through Pi JSONL; tests cover branch navigation, resume and export/import. `PiSharpToolExecutionContext.ExecuteToolAsync` invokes the same wrapped MAF functions as model calls, with hierarchical IDs, parent-linked lifecycle/progress, cancellation, durable tool intent/outcome, bounded nested-call metadata, and compaction/session JSONL/HTML/TUI projections. Focused tests cover multi-level invocation, child failures, root-only MAF results and nested file operations during compaction. The shared pipeline now supports reusable async extension call/result hooks and allow/block decisions for root and nested invocations. Outputs still lack output-schema/structured-content and explicit returned-error semantics. There is no Codemode, tool-search or MCP runtime, and model selection routes directly through `ModelRuntimeController`/`ProviderModelRuntime` without a separate logical virtual-model contract.

The installed packages are Microsoft Agent Framework `1.21.0` and Microsoft.Extensions.AI `10.10.0`. Per-run `ChatClientAgentRunOptions` tools merge with agent-level tools, so the implementation keeps all allowed invokable functions registered with MAF and rewrites only the outgoing request declarations in `ObservedChatClient`. A deterministic multi-request tool test proves a loadout change made by one tool is visible on the next request; `DurableToolFunction` enforces reachability even if a provider returns an undeclared call. Nested invocation still needs its own shared execution boundary. Do not let generated code execute in the PiSharp host process; the sandbox boundary must be deliberate and resource-limited.

The registry/loadout and shared nested-execution slices are implemented. This slice adds reusable asynchronous call/result hooks and allow/block decisions to the common root/nested pipeline; focused integration coverage verifies mutation, denial before execution, result replacement and parent identity, and the full local suite passes. Structured-result/error contracts remain open: add output schemas and explicit returned error results before building tool search and sandboxed Codemode, followed by MCP and virtual-model routing. Current Pi built-ins themselves load through extension resources, so PiSharp's native-extension lifecycle/resource model must support reusable built-in registrations rather than private special cases. Virtual-model routing remains distinct and must preserve logical/physical model identity across runtime, persistence, compaction, usage, sessions and UI.
