## PiSharp gap and implementation order

PiSharp currently constructs a fixed `ChatOptions.Tools` array in `PiAgent` and wraps functions in `DurableToolFunction`. `ExtensionRegistration` currently exposes native .NET tools, commands, renderers and direct-Bash handlers; it does not provide a session tool registry, exposure states, loadout hooks, or nested invocation context. `ConversationRun` persists top-level tool events/results but has no parent-linked nested-call record. There is no Codemode, tool-search or MCP runtime, and model selection routes directly through `ModelRuntimeController`/`ProviderModelRuntime` without a separate logical virtual-model contract.

The installed packages are Microsoft Agent Framework `1.21.0` and Microsoft.Extensions.AI `10.10.0`. The local skill documents per-run `ChatClientAgentRunOptions` tools as merged with agent-level tools, so it is not by itself a replacement mechanism for Pi's per-request loadout. Preserve the MAF tool invocation loop and determine the request-time declaration/execution seam with deterministic tests before building Codemode or MCP. Do not let generated code execute in the PiSharp host process; the sandbox boundary must be deliberate and resource-limited.

The first implementation slice is the general registry and per-session loadout, followed by one shared nested invocation pipeline and durable event/result projection. Codemode, tool search, and MCP must consume these contracts. Virtual-model routing remains a distinct later capability and must preserve the logical/physical model distinction across runtime, persistence, compaction, usage, session projections and UI.
