## PiSharp gap and implementation order

PiSharp now has a general `PiSharpToolRegistry` with immutable registered/callable/declared projections; all five exposure states; prepare-loadout description and declaration filtering; extension registration metadata; per-`AgentSession` loadouts; request-time MAF tool declaration projection; an extension execution context for changing active tools; and a fail-closed invocation guard. Deterministic tests show a model-only orchestrator activating a deferred tool for the next provider request, isolation between sessions, and rejection of an undeclared hidden-tool call. Active declaration state is not persisted through transcript/tree/resume yet. Nested execution, correlated child events and persisted nested-call records remain unimplemented. There is no Codemode, tool-search or MCP runtime, and model selection routes directly through `ModelRuntimeController`/`ProviderModelRuntime` without a separate logical virtual-model contract.

The installed packages are Microsoft Agent Framework `1.21.0` and Microsoft.Extensions.AI `10.10.0`. Per-run `ChatClientAgentRunOptions` tools merge with agent-level tools, so the implementation keeps all allowed invokable functions registered with MAF and rewrites only the outgoing request declarations in `ObservedChatClient`. A deterministic multi-request tool test proves a loadout change made by one tool is visible on the next request; `DurableToolFunction` enforces reachability even if a provider returns an undeclared call. Nested invocation still needs its own shared execution boundary. Do not let generated code execute in the PiSharp host process; the sandbox boundary must be deliberate and resource-limited.

The first implementation slice now covers the general registry and per-session request loadout. It does not close the loadout task because declarations do not yet survive resume/fork. Next, add one shared nested invocation pipeline and durable event/result projection, then persist active declaration changes. Codemode, tool search, and MCP must consume these contracts. Virtual-model routing remains a distinct later capability and must preserve the logical/physical model distinction across runtime, persistence, compaction, usage, session projections and UI.
