## PiSharp gap and implementation order

PiSharp has a general `PiSharpToolRegistry` with immutable registered/callable/declared projections, five exposure states, prepare-loadout behavior and per-session loadouts. Loadout events persist through branches and Pi JSONL. `PiSharpToolExecutionContext.ExecuteToolAsync` invokes the same wrapped MAF functions as model calls, with parent-linked lifecycle, cancellation, durable intent/outcome and bounded nested metadata. Root and nested calls share async hooks, allow/block policy, output-schema validation and the structured result contract. `ExtensionCatalog` resolves `builtin:<name>` definitions through the regular source/trust/enable path for Codemode and tool-search; explicit loading, `--no-extensions`, disable overrides, and stable source identity have local tests. MCP configuration, transports, tool/resources, OAuth, per-server reconnect, one expired-session retry and safe transient resource retry now exist; lifecycle tests pass 3/3 locally. MCP is still initialized outside the normal built-in resource/enable path, and dynamic refresh, management and extension registration remain. `tool_search` ranks callable deferred/Codemode tools and activates matches through the persisted loadout; local provider-loop tests cover next-request declarations and resume. `codemode` uses a fresh QuickJS/WASM VM outside the PiSharp process, only exposes callable tools, and persists successful script store state on the selected branch. Model selection still has no separate logical virtual-model contract.

The installed packages are Microsoft Agent Framework `1.21.0` and Microsoft.Extensions.AI `10.10.0`. Per-run `ChatClientAgentRunOptions` tools merge with agent-level tools, so the implementation keeps all allowed invokable functions registered with MAF and rewrites only the outgoing request declarations in `ObservedChatClient`. A deterministic multi-request tool test proves a loadout change made by one tool is visible on the next request; `DurableToolFunction` enforces reachability even if a provider returns an undeclared call. Nested invocation still needs its own shared execution boundary. Do not let generated code execute in the PiSharp host process; the sandbox boundary must be deliberate and resource-limited.

The registry/loadout, nested execution, structured-result, built-in registration, tool-search, bounded Codemode runtime and MCP disconnect/session recovery slices have landed. Current work resumes notification-driven dynamic tool/resource updates, `/mcp` management, `builtin:mcp` integration and extension registration. Then implement logical/physical virtual-model routing and Codemode model/classifier semantics. The wider extension lifecycle, context transforms, provider/model registration and UI contracts still need work. Virtual-model routing must preserve logical/physical identity across runtime, persistence, compaction, usage, sessions and UI.
