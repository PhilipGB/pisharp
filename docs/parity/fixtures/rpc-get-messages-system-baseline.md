# RPC `get_messages` generated system-message comparison

Reference: Pi `0.87.1`, source `earendil-works/pi@2b0a123de98318c2ff8069661721ce0c3794c34e`.

Paired Pi/PiSharp CLI process comparisons queried `get_messages` after cloning an active run and while a provider stream was blocked after a `message_update`. Both returned the same visible session messages and lifecycle order. In the blocked-stream comparison, both reported `messageCount: 4` and four `get_messages` records: the system message, two completed messages, and accepted prompt. The partial assistant text remained in lifecycle events and was not yet in `get_messages` or `get_last_assistant_text`. PiSharp now follows that session snapshot boundary.

The projected message uses `role: "system"`, an empty `content`, a positive timestamp, PiSharp's actual MAF instructions in `sections.preamble`, and `toolsAdded` entries containing the selected tools' names, descriptions and parameter schemas. It appears only after the provider run initializes the prompt; a fresh session still reports zero messages. The generated message is not added to the canonical C# session or Pi JSONL. In-flight assistant deltas remain visible through `message_update`; the live assistant is not added to `get_messages` before its `message_end`.

Pi's generated message in this process used the `preamble`, `tools`, `rules`, `docs`, and `cwd` sections. PiSharp currently places its actual combined MAF instruction string in `preamble`; the two section layouts are observably different. Exact system-prompt section projection and broader contexts remain open.

The source behavior is visible in Pi's [`get_messages` handler](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/modes/rpc/rpc-mode.ts) and [`AgentSession.messages`](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/agent-session.ts). `RpcActiveCloneProcessTests` verifies fresh-session omission, post-run projection and message count. `RpcReadCommandsProcessTests.SessionReadCommandsReturnOneSnapshotWhileProviderRequestIsBlocked` verifies active `get_messages` excludes partial assistant output, `get_state.messageCount` equals the four-message snapshot, and `get_last_assistant_text` remains the prior completed answer; it also verifies the partial stays in the event stream. `RpcMissingSessionTargetProcessTests` verifies the count after a completed turn.
