# Session crash recovery and writer-lock differential

Historical paired reference: Pi 0.87.1 at `2b0a123de98318c2ff8069661721ce0c3794c34e`. The current-main replay below used Pi `6f7551516b84278eb9da1c340c8e7bc66be1a6ba` on 2026-09-28. Both runs used an OpenAI-compatible tool call that performed one append-only side effect and killed the CLI before a tool result could be persisted; the process then reopened the same session and sent a continuation request through a local SSE fixture.

| Observation | Pi | PiSharp |
|---|---|---|
| Persisted at crash | User message and assistant `toolUse` call; no tool result | User and assistant call plus durable `tool_intent`; no `tool_outcome` |
| Startup recovery | Does not replay the tool; exposes the unfinished call | Appends `run_recovered` and a user warning that the Bash outcome is unknown; does not replay the tool |
| Continuation request | `system, user, assistant(tool call), tool("No result provided"), user` | Same valid tool-result projection, followed by the recovery warning and new user prompt |
| Side effect and process outcome | File contains exactly `x`; restarted CLI exits 0 | File contains exactly `x`; restarted CLI exits 0 |

The request comparison exposed a provider-history gap: Pi inserts a synthetic tool result for an orphaned call, while PiSharp previously sent the recovery user message directly after the call. `ObservedChatClient` now fills missing results only in its provider-boundary projection, including the context-overflow retry path. The synthetic result is absent from RPC `get_messages` and the durable session; the recovery warning remains visible. This matches Pi's request shape while retaining PiSharp's stronger durable uncertainty warning and no-replay behavior. See Pi's current [session manager](https://github.com/earendil-works/pi/blob/6f7551516b84278eb9da1c340c8e7bc66be1a6ba/packages/coding-agent/src/core/session-manager.ts) and [message transformer](https://github.com/earendil-works/pi/blob/6f7551516b84278eb9da1c340c8e7bc66be1a6ba/packages/ai/src/api/transform-messages.ts).

## Current-main recovery and writer-concurrency replay

On Pi `6f7551516b84278eb9da1c340c8e7bc66be1a6ba`, a real CLI received the same `crash-window-fixture` Bash call as `CrashRecoveryProcessTests.CrashAfterToolSideEffectBeforeOutcomeCheckpointRecoversWithoutReplayingTool`: the command wrote one `x` marker and killed the first process before the result entry. The saved JSONL held three messages, including the assistant tool call and no result. A second Pi process received the same continuation prompt; its provider request roles were `system, user, assistant, tool, user`, with `No result provided` immediately after the orphaned call. The restarted CLI exited 0, stderr was empty, and the side-effect file still contained exactly `x`. The matching PiSharp process test passes and additionally verifies `run_recovered`, the durable unknown-Bash warning, and the absence of a synthetic result from RPC/session history.

A two-process probe opened the same current-Pi JSONL session through separate `SessionManager.open` instances before releasing both writers. Both appended valid rows as sibling branches under the same parent; no session writer lease or stale-snapshot fence exists in Pi's `session-manager.ts`. PiSharp deliberately uses a bounded same-process semaphore plus an OS lock and hash check: the lock-wait process test verifies writes serialize, and `ConversationSessionTests.ConcurrentStoresRejectStaleWrites` verifies that a stale snapshot is rejected rather than merged as a branch. The path-alias gate race found earlier remains fixed. This is an intentional safety difference; macOS locking still needs native execution.

Current Pi `loadEntriesFromFile` and `session-manager/file-operations.test.ts` skip malformed rows and append a newline after an unterminated final row. The PiSharp JSONL importer also skips malformed rows but imports into a separate native session and leaves the source bytes unchanged. Upstream `file-operations.test.ts` plus `agent-session-concurrent.test.ts` passed 40/40; PiSharp recovery/lock/JSONL focused checks passed 7/7, and the stale-writer check passed 1/1.

The concurrency audit found that the POSIX byte-range lock serialized separate processes but not two `SessionFileLease` acquisitions inside one Linux process. A fail-first unit test reproduced the race. PiSharp now combines a bounded, cancellation-aware per-path process semaphore with its existing OS-level lock and store hash fencing. The cross-process lock-wait fixture and new same-process lease fixture both pass. Current Pi's session manager appends JSONL rows without a sibling lock; PiSharp deliberately keeps stale-write protection.

On macOS, [.NET documents `FileStream.Lock` as unsupported](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.lock?view=net-10.0). PiSharp's macOS path instead uses `FileShare.None`'s exclusive `flock`, then explicitly verifies native lock support so an unsupported filesystem fails closed; the [.NET runtime implementation](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/Microsoft/Win32/SafeHandles/SafeFileHandle.Unix.cs) otherwise ignores unsupported-lock errors when opening with `FileShare.None`. The cross-process fixture is enabled for Linux and macOS, but this run executed on Linux; the macOS path still needs a native macOS run.
