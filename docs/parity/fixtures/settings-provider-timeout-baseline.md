# Provider request and idle timeout settings

## Pi reference

At pinned Pi `2b0a123de98318c2ff8069661721ce0c3794c34e`, `httpIdleTimeoutMs` defaults to 300000 ms. It configures Undici's response-header and response-body idle limits; zero disables those dispatcher limits. Pi also forwards an effective request timeout to every provider stream: an explicit `retry.provider.timeoutMs` wins, otherwise the HTTP idle setting is used, with `httpIdleTimeoutMs: 0` mapped to `2147483647` ms. Settings in `.pi/settings.json` override the user settings file, and `/settings` persists both controls in user scope.

Pi's `/settings` picker exposes `httpIdleTimeoutMs` at user scope. `retry.provider.timeoutMs` is read from the settings JSON but is not a row in the pinned picker. Pi's `transport` setting defaults to `auto` and offers `sse`, `websocket`, and `websocket-cached`. In the pinned implementation, that option changes behavior in the `openai-codex-responses` adapter; the regular OpenAI Responses, OpenAI Completions, and Anthropic adapters do not implement that WebSocket path. The relevant pinned sources are [`sdk.ts`](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/sdk.ts), [`http-dispatcher.ts`](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/http-dispatcher.ts), [`settings-manager.ts`](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/settings-manager.ts), and [`openai-codex-responses.ts`](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/ai/src/api/openai-codex-responses.ts).

## PiSharp behavior

PiSharp parses nonnegative provider request timeouts and HTTP idle timeouts, including the `httpIdleTimeoutMs: "disabled"` spelling, and floors fractional idle values as Pi does. Trusted project values override user values. The `/settings` picker edits the idle timeout and provider request timeout; changing either replaces the provider runtime for the next request. The provider request setting overrides the request deadline, while the idle setting supplies its fallback and controls the streaming update-idle deadline. CLI-created agents disable PiSharp's separate MAF retry loop because the provider SDK adapter already applies `retry.provider.maxRetries`; otherwise a failed timeout was retried outside the configured count.

The OpenAI SDK receives `OpenAIClientOptions.NetworkTimeout`; Anthropic receives its per-call `Timeout`, with `HttpClient.Timeout` disabled so it cannot preempt the SDK setting. A shared `ProviderRequestTimeoutChatClient` also enforces a total request deadline and resets the streaming idle timer after each emitted `ChatResponseUpdate`. It forwards the optional raw OpenAI tool-call-delta capture interface so timeout decoration does not change RPC fragments or provider error projection.

## Evidence and limits

`ProviderChatClientFactoryTests.ProviderTimeoutSettingCancelsAStalledLoopbackResponse` and `ProviderChatClientFactoryTests.ProviderStreamIdleSettingCancelsAStalledLoopbackStream` exercise real OpenAI Responses and Anthropic SDK requests against local HTTP servers. `ProviderRequestTimeoutTests` checks timer reset and caller-cancellation propagation. `ProviderTimeoutProcessTests.SavedProviderTimeoutStopsARealCliRequest` starts the CLI with persisted settings, accepts every request at a local server, and verifies the default provider retry count permits exactly one attempt before timeout. `UserSettingsTests.ProviderRetrySettingsAreSeparateValidatedAndMergedByScope`, `UserSettingsWriterTests.UpdatesSupportedValuesAndPreservesOtherSettingsAtomically`, and `TerminalPtyTests.SettingsPickerEditsUserScopeThroughLinuxPty` cover precedence, validation, persistence, and the picker. The RPC tool-call-delta and pre-content overflow loopback fixtures also verify that the timeout decorator preserves optional provider capabilities and failure projection.

For process-level comparison, the Pi bundle built from pinned source `2b0a123de98318c2ff8069661721ce0c3794c34e` and the PiSharp CLI used the same local OpenAI Responses endpoint, `retry.provider.timeoutMs: 300`, `httpIdleTimeoutMs: 5000`, and a server that delayed its response by 1800 ms. Pi sent one request and exited with `Request timed out.` 313 ms after the server accepted it; PiSharp sent one request and exited with `The provider request timed out after 300 milliseconds.` 277 ms after acceptance. Both exited with status 1 before the delayed response, so the persisted settings and effective request deadline matched for this case. The exact pinned worktree was built from its lockfile; its ignored model catalog data was hydrated for the build, while the fixture selected an explicit custom provider and did not use the catalog.

PiSharp's streaming idle timer observes parsed response updates; Pi's Undici dispatcher observes wire-level response bytes and headers. An upstream keepalive or partial SSE payload that produces no parsed update can therefore time out earlier in PiSharp. The OpenAI SDK network timeout and Anthropic request timeout add their own bounds, but this fixture does not claim exact wire-byte idle parity.

`transport` remains unsupported in PiSharp: the active C# adapters do not include Pi's `openai-codex-responses` WebSocket implementation, so exposing the setting would currently create a no-op control. WebSocket transport and `websocketConnectTimeoutMs` remain separate ledger items.
