# Full terminal differential harness

The runner launches the real pinned Pi source CLI and the built PiSharp CLI in independent controlling PTYs. Both receive the same dimensions, locale, terminal colors, model, deterministic local provider, working directory and fixture actions. No credentials are inherited. The stable empty working directory is `/tmp/pisharp-terminal-fixture-workspace`; a harness marker and advisory lock prevent concurrent scenarios from sharing it. Each product receives freshly reset configuration in the harness-owned `/tmp/pisharp-terminal-fixture-agent`, so temporary session paths do not change between runs. Both fixed directories require a harness marker; foreign directories are refused.

```sh
npm ci --prefix tools/parity/terminal --ignore-scripts --no-audit --no-fund
npm test --prefix tools/parity/terminal
python3 -m unittest discover -s tools/parity/terminal -p 'test_*.py'
python3 tools/parity/terminal/run.py --pi /tmp/pisharp-current-pi \
  --calibrate --output artifacts/parity/startup-calibration
python3 tools/parity/terminal/run.py --pi /tmp/pisharp-current-pi \
  --output artifacts/parity/startup-comparison
python3 tools/parity/terminal/assert_streaming_markdown_exit.py \
  artifacts/parity/streaming-markdown-comparison/report.json
```

Build PiSharp first. Pi must have its workspace dependencies installed. `--pisharp` selects another built DLL; `--fixture` selects a reusable JSON scenario; `--case 80x24-dark-fullscreen` selects one matrix case. Exit code 0 means all selected checkpoints match; exit code 1 means a product mismatch or an incomplete product scenario. Calibration compares two independent executions of Pi and must pass before relying on cross-product evidence. There is no option to turn product mismatches into success.

For compiled native package fixtures, provide `--pisharp-extension` with the built assembly and set `pisharpExtension: true` plus `pisharpNativeExtensionPackage` metadata (`id`, `version`, and entry `type`) in the fixture. The runner places the assembly and adjacent `.deps.json` in an isolated installed-package layout and writes its manifest/archive into that case's agent directory. Pi never receives the C# assembly. Fixtures without `pisharpNativeExtensionPackage` retain the legacy direct `--extension` assembly path.

Use a distinct directory under `artifacts/parity/` for each generated run. Git ignores this output; it persists locally but needs a separate backup for long-term retention. Select reviewed compact reports/assertions and pinned notes for `docs/parity/fixtures/` when recording evidence. Raw streams stay in the local output directory. See the [evidence storage policy](../../../docs/development/verification.md#parity-evidence-storage).

Each checkpoint captures every viewport cell's characters and width, foreground/background color modes and values, all text attributes, underline style/color and hyperlink. It also records cursor coordinates, visibility, style/blink, active screen, complete normal/alternate buffers with scrollback and wrapping, terminal/input/mouse/focus/paste/keyboard/synchronized-output modes, and default colors. The emulator captures every completed synchronized-output frame with the same full terminal state. The comparison checks named checkpoints and each rendered state transition, collapsing only adjacent identical snapshots and cursor coordinates while that cursor is hidden. Per-checkpoint control buckets are retained for diagnosis, because an asynchronous write can land on either side of a readiness checkpoint. The complete raw stream and its exact match status remain in the evidence and report, including redundant redraw bytes whose scheduling can differ. Fixtures may declare a concurrent request batch unordered only when both current Pi and PiSharp source launch those requests concurrently; request identity/count stay exact, and order around each batch remains exact. Clipboard, image and other string escape payloads remain intact. Image pixel rendering still needs dedicated image fixtures and terminal-profile evidence; captured escape payloads alone do not prove image appearance.

The runner limits itself and its child processes to two available CPU cores where affinity controls are supported, and caps common Python, .NET, Node, and native thread pools at two. It spools named checkpoints and synchronized render frames through compressed temporary files, compares checkpoints one at a time, then copies those gzip streams directly into per-product `.frames.jsonl.gz` and `.renders.jsonl.gz` evidence files. The main `.json.gz` capture points to those complete frame streams and retains raw bytes and HTTP traces. Each case also writes a compact `.assertions.json.gz` companion containing only fixture-selected checkpoints and HTTP traces; assertion scripts use it instead of expanding the multi-gigabyte capture. This keeps paired CLI runs and their worker allocations bounded on developer machines and in CI.

The emulator is pinned to `@xterm/headless@5.5.0`, the dependency used by current Pi's virtual-terminal tests. Public buffer/cell/parser APIs provide most state. The pinned cursor visibility, extended underline and hyperlink accessors are internal xterm APIs, covered by contract tests. Replies to cursor/device/color queries feed back into the PTY; the emulator supports controlled legacy and Kitty profiles. Initial interactive fixtures use Kitty to avoid an asynchronous legacy-negotiation escape-order race; that race is retained in the earlier calibration evidence, rather than normalized.

Fixtures can override per-product CLI arguments, set controlled environment values and seed files within each fresh agent directory for authentication, sessions, keybindings and resource scenarios. File bodies can use `{workspace}` for the selected harness workspace, including when `--fixture-root` isolates a run. Fixture actions can also update owned workspace/agent files between interactions, which supports real `/reload` workflows. The local HTTP fixture accepts streamed OpenAI-compatible chat requests and retains their complete request bodies for tool/resource assertions. Actions can send exact UTF-8/escape input, resize the terminal, wait for a product-specific readiness predicate, and capture process exit/restored-screen state. Predicates select a checkpoint; they never rewrite compared cells. Settling waits for output quiescence and an expected viewport condition, with a bounded timeout; `expectCursorChange` additionally waits for the cursor coordinates to change after the action when the visible text itself already existed before input. Named checkpoints give deterministic intermediate frames. When an explicit gate has established readiness, `allowStaticFrame` captures an unchanged screen without waiting for more terminal bytes, which verifies stable in-flight UI while a fixture holds a request. Long-running animated interactions require deterministic progress/clock fixtures before their sequences can be claimed as matched.

`assert_streaming_markdown_exit.py` checks the pinned streaming fixture's named exit checkpoint for normal-screen restoration, visible cursor, inactive temporary input/mouse/synchronized-output modes, and exact normalized terminal-state parity. The Python driver also protects the fixture's double-Ctrl+C exit action from accidental removal.

`terminalPrelude` writes the same literal bytes to both PTYs before either CLI starts. Use it to seed the primary screen and scrollback for normal-buffer restoration scenarios; it runs through a small shell wrapper, then replaces that shell with the tested CLI.

The Linux `jobControl` terminal profile gives the CLI its own foreground process group under the existing PTY. Its supervisor waits for SIGTSTP, verifies that canonical input, echo and signal handling match the original terminal settings, and exposes a `suspended:tty-restored` checkpoint. Sending `resume` followed by a newline returns the foreground to the CLI and delivers SIGCONT. Cleanup resumes and kills the owned child group if a fixture fails while suspended; a native CLI PTY regression and a Python cleanup test cover this boundary.

`terminal-mouse-multiclick.json` covers fullscreen word selection, line selection,
and a word-granularity drag. Each click sequence is sent in one input action to
exercise Pi's 500 ms multi-click window without depending on the time spent
capturing the previous checkpoint. Exact OSC 52 payloads and decoded styles are
checked; click expiry, source-path tokens, combining characters, and wide emoji
also have deterministic native regressions.

`report.json` contains the source pins, terminal and request match results, raw HTTP match/difference paths, exact raw-byte match status and first raw difference, exact synchronized render counts and mismatch counts, checkpoint-control boundary differences, a bounded sample of mismatch paths, and scenario failures. Each case's `.json.gz` index points to separate per-product checkpoint and synchronized-render JSONL streams, and contains controls, raw terminal output and observed fixture HTTP requests in arrival order. Raw bytes and request identities remain in full; visual state comparison preserves cells, styles, visible cursor placement, modes and transitions. It canonicalizes only empty cells whose character is serialized as either `""` or `" "`; width, colors and attributes remain exact. It also ignores hidden cursor coordinates and adjacent duplicate render states. Request ordering remains exact except within explicitly declared concurrent batches. HTTP comparison canonicalizes only Pi's generated `Main documentation`, `Additional docs`, and `Examples` package-root lines in system messages. A same-Pi calibration with an equal-length `PI_PACKAGE_DIR` alias proves that these environment paths can change while the terminal state stays exact; the complete original request body and raw HTTP difference remain in the capture and report. The runner supplies deterministic prose and a stable working directory rather than editing their rendered output.

The initial reusable fixtures cover startup, editor input/movement/paste, resize, regular/fullscreen intent and terminal restoration; deterministic user/assistant/Markdown transcript rendering; and model/settings selectors. These fixtures expose remaining product gaps and do not establish complete TUI parity. Add scenarios to this harness as capability families close, including tools/Bash/thinking/session/tree/fork/authentication/MCP/trust/search/selection/clipboard/images/errors/aborts/keybindings/easter eggs. The full ledger requirement remains in progress until that breadth is verified.

PiSharp supports both `tuiMode: fullscreen` and `tuiMode: regular` from user settings. Fullscreen uses the alternate screen; regular mode renders into the main screen and scrollback. Keep calibrated paired fixtures for both modes because startup, idle footer updates, viewport sizing and shutdown differ between them.
