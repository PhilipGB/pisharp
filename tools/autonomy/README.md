# Opt-in autonomous implementation controller (development infrastructure)

The original plan is **not present** after the heading in the request that called for this supervisor. `docs/parity/execution-ledger.json` is therefore a **provisional** inventory bootstrapped from the existing pinned parity matrix, detailed command/flag/RPC/keyboard/settings inventory and the current request. `plan_received: false` prevents a successful completion claim even if all provisional tasks are marked verified. Incorporate the actual plan when supplied; preserve `required_ids` and add every new item. Only Pi Packages may be excluded. Do not change `plan_received` merely to unblock completion.

This controller is an **external Pi RPC supervisor**, not an extension hook. Pi's `agent_before_settle` can request a further model call in the active run if context permits; `agent_settled` is notification-only. The supervisor listens for correlated `prompt` acceptance followed by `agent_settled`, checks the ledger on disk, and dispatches the next requirement. It does not mistake `agent_end`, a commit or a model assertion for project completion. It uses the installed Pi 0.87.1 RPC protocol, a private persistent Pi session directory, and one durable state file under `.pisharp-autonomy/`. It never stores provider keys. The worker must write actual evidence and commit/push the ledger along with changes. This is not a PiSharp product feature.

Run the credential-free controller fixture before activation:

```sh
python3 -Werror::ResourceWarning -m unittest discover -s tools/autonomy -p 'test_*.py' -v
```

The subprocess fixture demonstrates automatic dispatch after settlement while another requirement remains, a stop after all required work passes its gate, restoration of the durable ledger after a restart without repeating a verified task, recovery from a worker crash, a non-repeating stalled-task policy, single-worker locking and a missing-plan gate. It **does not** exercise paid model inference or prove real project completion.

## Production lifecycle

The committed `pisharp-autonomy.service` is a user-level systemd unit for this specific checkout. Activate only after the current Pi session has stopped editing the repository. Run `systemctl --user link <absolute-path-to-service>`, `systemctl --user daemon-reload` and `systemctl --user start pisharp-autonomy.service`. Do not start the service while another writer is active: the flock protects **only controllers and their child workers**; an unrelated Pi process cannot be forced to honor it. The worker inherits the flock descriptor to avoid concurrent supervisors if the controller dies but its child survives. Systemd manages process-group shutdown and restarts on the bounded dispatch budget; exits 2/3/4 are intentionally not restarted. Test activation via `systemctl --user status` and inspect `.pisharp-autonomy/state.json` to confirm a real worker dispatch and settlement before describing it as operational. `journalctl --user -u pisharp-autonomy` reports service failures. Stop via `systemctl --user stop pisharp-autonomy` before doing manual repo edits. The controller has **not** been verified to survive a machine shutdown without a systemd user linger session; do not claim this without testing it.

The configured model is the user's authenticated `openai-codex/gpt-5.6-sol` at high reasoning via the installed Pi CLI, not the PiSharp test endpoint. Startup uses `--offline` to avoid model refresh, not to bypass authentication or limits; a real auth failure is an error. No cloud credentials are forwarded to a custom URL. The worker can use the pinned Pi checkout for behavioural reference, and PiSharp still uses MAF. The controller validates the existence of recorded acceptance, implementation, evidence and the known requirement set; evidence **must be independently inspected** before setting `final_audit.complete`, followed by the final test gate. This gating alone does not prove full upstream parity.

### Quota incident (2026-09-24)

A real supervised Pi session completed three verified slices, then the Codex provider reported **“The usage limit has been reached”** in assistant `message_end` records. The initial controller wrongly treated every `agent_settled` as success, repeatedly prompted unrelated ledger items, exhausted its attempts and stopped (exit 4). No further model work occurred on those attempts. The controller now checks the final assistant stop reason and stops on quota/auth/billing failures without dispatching more work. Fixture tests cover quota and generic provider errors. The ignored runtime state preserves the exhausted attempts as forensic evidence; it must not be reset merely to work around the genuine limit. Do not restart the paid worker until access is restored; confirm independently first. Uncommitted provider/model work from the interrupted slice was reviewed and fixed manually; the full provider/auth parity requirement remains unverified.

The state records task selection, attempts, failure and settled outcomes, Git HEAD before/after, final validation and stop reason. On restart, an interrupted task is instructed to inspect the working tree/ledger rather than repeat side effects. A task that settles with no new commit and no verification is not prompted again unchanged; after three failures the controller moves to other work. If nothing actionable remains it exits 4 with unfinished tasks. Exit 5 is a finite per-process dispatch budget; systemd restarts with backoff. Genuine provider limits, repeated errors, missing authoritative plan and other blockers cannot be bypassed. The worker session is a Pi session, not the application's own persistence format. Only one worker may modify the repository while active.
